## 背景：Karpathy 的 LLM Wiki 与落地困境

近期 Karpathy 提出的 LLM Wiki 概念引发广泛讨论，但它本质上是一套方法论，而非可落地的方案。Google 紧随其后推出的 OKF（Open Knowledge Framework）则为该方向提供了标准化定义，但也只搭出了指导框架，并未给出对应的实现工具。

正是为了填补这一空白，作者开源了一个名为 Wiki Graph（.wikg 文件格式）的知识归档工具，作为 LLM Wiki 更底层、可分享、可追溯的知识底座。

## RAG 的工作原理与瓶颈

### 经典 RAG 流程

过去两三年里，人们谈到知识库时首先想到的方案就是 RAG（Retrieval-Augmented Generation）。其标准流程如下：

1.  将原文（文章、书籍）切分为一段一段的文本片段；
2.  用 sentence embedding 把每个片段压缩成一个向量，向量蕴含该片段的全部语义特征；
3.  查询时，AI 把用户问题用相同的 embedding 模型编码为向量；
4.  将该向量与向量数据库中存储的所有向量做相似度比较；
5.  按相似度排序后，把排名靠前的原文片段拼起来交还给 AI 生成回答。

![[01_raw/_inbox/文章/images/4d6417826df148a88819160adb8e0e98_MD5.jpg|RAG 流程图：原文切分、向量编码、相似度检索]]

RAG 流程图：原文切分、向量编码、相似度检索

### RAG 在专业领域的失灵

RAG 用了几年后，大家普遍感觉"也就那样"，尤其在法律、医学这种对准确性极度敏感的行业，召回质量常常不尽人意。

问题的根源在于 RAG 对"知识相似度"的判定方式：它默认"向量空间中距离接近即语义相似"，依赖的是多维空间中的几何距离。然而知识天然具备语义关联，单靠数学距离难以表达真实的知识组织结构。

## Karpathy LLM Wiki 的核心思想：让 X 成为可定义的 Schema

Karpathy 不再纠结"知识应该如何被组织"这个未知数 X，转而提出一个更根本的方案——你跟 AI 聊，自己把规矩定下来。

### Schema：人与 Agent 的约定

Schema（模式）是人与 AI Agent 之间的一个约定：你规定这些知识要按某种结构组织，AI 就按这个规矩把知识整理成相应的形态。一旦 schema 敲定，它就成了最适合你场景的知识表示方式。

换言之，你想要什么样的关联关系，就说出来；说不清楚，就和 AI 聊，让 AI 当"知心大姐姐"帮你梳理感觉，最后你们一起把 schema 的标准定下来。

### RAG 是预制菜，Karpathy 是自助餐

这一思路的差异可以用一个比喻概括：

-   RAG 的 X 是预制菜：向量距离已经定死，最多换一种 embedding 模型或距离算法；
-   Karpathy 的 X 是自助餐：食材和大厨已经就位，怎么搭配由你自己和大厨商量。

从交互上看，LLM Wiki 与几年前的 RAG 并无本质区别——仍然是 AI 通过查询与知识库对话，再基于资料回答用户。区别仅在于原本那个被预制的 X，变成了可由人定义、且与 AI 协商得出的 schema。

## 司马迁的启示：第一部维基百科

LLM Wiki 的本质，是让 Agent 帮你把线性材料"编纂"成一个个 Wiki 页面。这种行为并非新生事物——司马迁在两千多年前就已经做过。

### 从编年体到纪传体

在司马迁之前，史书多为编年体（如《资治通鉴》），按时间顺序逐年记事，本质上是流水账式的线性记录。司马迁在编纂《史记》时做了一个关键转变：

-   把散落在编年体中的同一人物生平事迹抽取出来；
-   为该人物编成一个独立词条（列传）；
-   形成"廉颇蔺相如列传""项羽本纪"这类结构。

纪传体的核心价值在于：每一条知识都可追溯到原始记录，保留了完整的证据链——你想看原文，仍能找到出处。

## Wiki Graph：为 LLM Wiki 补齐可分享的底座

LLM Wiki 存在两个显著短板：一是知识库太私人，无法分享；二是依赖 Agent 做实体提取，成本过高且容易偷工减料。Wiki Graph 正是为解决这两个问题而设计。

### 补齐可分享性

LLM Wiki 的知识库是与 AI 唠出来的，高度私人化。你想把《西游记》的整理成果分享给别人时，往往会和你的工作日报、周报以及杂乱的私人信息混在一起——等于要把整个"第二大脑"拱手让人，这显然不现实。

Wiki Graph 的做法是把知识库的颗粒度下沉：

-   在 Google OKF 中占据 sublayer（南向层）位置；
-   提前从原文中提取实体（Entity）和主谓宾三元结构；
-   实体对齐到维基百科的 QID，确保每个概念在公共语义中有精确、无争议的位置；
-   将一组文档封装为相对封闭的 .wikg 知识归档文件；
-   他人可通过 U 盘或文件传输直接接管这份归档，不会出现"分法不一致、不兼容"的问题。

这种对齐维基百科的主谓宾三元结构稍加修饰，就能直接套用 Karpathy 的 schema，因此两者并不冲突。

### 补齐成本与覆盖完整性

让 Agent 全程主导实体提取时，Agent 会本能地偷工减料——并非敷衍，而是真正"撸起袖子大干一场"会让用户的钱包吃不消。结果是 Agent 不会真的把整本书扫完。

Wiki Graph 的应对策略是把 Agent 方案退回 Flow 方案：

-   任务被简化为对齐维基百科——LLM 不必揣摩人类心思；
-   DeepSeek 在此场景下极其合适：实体召回精准、价格便宜；
-   用 Flow 把整本书的每一段话拆成主谓宾结构（如"关羽—斩—华雄"），逐句嵌入一个巨大的知识图谱网络。

知识图谱建好之后，上层 Agent 就能从已建好的图谱中直接抓取目标实体（例如"关羽"），列出全书所有相关原文，写词条时无需再翻全书。

## 为什么 Agent 不擅长扫书

Karpathy 设想的场景是短文——网页文章、十几页论文，Agent 全文过一遍恰到好处。但面对整本书时，就必须借助 Wiki Graph 这类工具。

如果让 Agent 直接扫描《三国演义》并提取关羽的所有人物关系，它会做这样的事：

1.  一开始一页一页地看；
2.  发现短期内没看到关羽，于是用 grep 全文检索；
3.  检索结果过多，开始写代码批量处理——这恰恰是问题所在。

> 代码可以处理结构化信息，但不能用来处理文学作品。一旦 Agent 这么做，结果就会失真。

而 Wiki Graph 用 Flow 扫书，所有内容都会被 AI 看到，不会漏掉任何段落。

## 总结：互补而非替代

Wiki Graph 与 Karpathy 的 LLM Wiki 不是对立关系，而是分层互补：

-   **Wiki Graph**位于底层（sublayer），负责将一本书或一组文档封装为包含原文、实体、主谓宾关系、证据链的 .wikg 归档；
-   **LLM Wiki**位于上层，负责让 Agent 基于 schema 编纂个人 Wiki。

上层 Agent 拿到这种覆盖全书、无巨细遗漏、可信且对齐公共语义的三元结构层后，编纂词条的效率会大幅提升。Wiki Graph 提供的 .wikg 归档既可以被 Agent 查询和使用，也可以被别人接管直接使用。

用一句话概括：

> Karpathy 让 Agent 编纂你的私人 Wiki，但私人 Wiki 太私、不便分享；Wiki Graph 做了更底层的事——它把一组文档封装成可分享、可追溯、能扫完整本书的知识归档，作为 LLM Wiki 的底座。

## 全文整理

Karpathy 的 LLM Wiki 最近很火，但它实际上并没有提供一套真正可以落地的方案。Karpathy 更多是给出了一个方法论：如果你真想搭建一个，可能找不到现成的方案。刚好 Google 又推出了 OKF（Open Knowledge Format），可以理解为它是为 Karpathy 的方向提供了一套标准化方案。但 OKF 同样没有实现，只是搭了个架子，教你该怎么做，却没有提供对应的工具。所以我干脆自己动手做了一套，因此这次开源了一个名叫 Wiki Graph 的项目。

先回到 Karpathy 的 LLM Wiki，有必要讲清楚它到底在解决什么问题。它本质上处理的是知识库的问题。两三年前提到知识库，大家都会想到 RAG。RAG 的做法是这样的：你有很多文章，可以理解为原文；要把这些文章或书籍变成一个知识库，需要用 RAG 把原文切成一段一段、一条一条的片段，然后用 sentence embedding 把它们压缩成向量。这个向量蕴含着该段文字的全部特征，存起来之后，搜索时 AI 会生成一个 query，再用相同的 sentence embedding 把这个 query 变成向量，和向量数据库里存储的向量进行比较，最后排出名次，把排名靠前的原文片段（因为已经裁好了）还给 AI，让 AI 去阅读。AI 如果对某些知识点感兴趣，也会进一步补充查询，流程大致如此。

但问题是，大家用 RAG 用了几年后，发现它组建的知识库也就那样，尤其是法律、医学这些对准确性要求极高的领域，用起来并不顺手。那么 Karpathy 的方案相对于 RAG 来说到底有什么优势？换句话说，RAG 到底弱在哪里？RAG 的弱点出在向量空间上。RAG 假定两个内容如果在向量空间里比较接近，它们就是相似的。所以当你搜索时，是通过 query 在向量空间里找到距离最近的片段，再返回给 AI。对于 AI 而言，这个组织方式，或者说判定知识彼此接近的标准，是一种数学上的、多维空间上的距离远近。

Karpathy 的思路则是从语义上的关联关系、从知识的组织结构出发，而不是依赖奇奇怪怪的向量空间语境。毕竟知识库里的知识天然包含语义。那么两个知识之间的接近程度该如何定义？知识本身应该如何被组织？Karpathy 压根不管这个问题，他的意思是：你自己决定怎么组织就行，你自己跟 AI 聊就行，何必来问我。这就是 Karpathy 的核心概念——schema。schema 其实是我们和 agent、和 AI 之间做的一个约定：我们说这些知识要按这个规矩组织，你就按这个规矩给我组织起来就行。AI 和 agent 跟我们聊着聊着，就把 schema 这个标准敲定了。一旦 schema 确定下来，它其实是最适合当前场景的。

向量空间用了这么多年，大家普遍觉得 RAG 不好用，那种关联关系不是我们真正想要的关联关系。Karpathy 的回应是：你想要什么，你说出来呀，你不说我怎么知道？你不是要找关联关系吗？那就把这些关联关系说出来；如果说不清楚，就跟 AI 聊天，让 AI 帮你找感觉，让 AI 当知心大姐姐跟你聊，最后由你和 AI 一起敲定 schema 的标准。所以 Karpathy 根本不在乎知识应该如何被组织，他认为这是一个未知数 x。原本这个 x 是什么意思，应该由你自己决定。

照这个思路做下来你会发现，Karpathy 的方案从交互上来说，和几年前的 RAG 知识库其实没有区别：还是识别、检索，然后还是通过 AI 间接地和知识库对答。只不过这里多出了一个 x。以前这个 x 是预制菜，RAG 说向量空间就是这个 x，就是向量之间的距离，最多只能换个更好的 embedding 模型，或者换一种计算距离的算法，爱吃不吃。而 Karpathy 的这个 x 是一桌自助餐，他把食材给你准备好了，大厨也准备好了，具体怎么做由你自己和大厨商量。这就是我觉得它有意思的地方。

回过头来说我为什么做 Wiki Graph：一方面是因为 Karpathy 这个东西压根没有实现；另一方面，我的文章就在那里，但有些场景下他的做法并不灵光，尤其从读书的角度来说。举一个例子：我在做《西游记》解读视频，要搞清楚孙悟空的所有人物关系，这个时候让 agent 去做，观察一下就会发现，agent 会用 grep 去扫，效率其实很低。但假设我提前把实体和关系提取出来，这件事就变成了另一种组织形式。你想想维基百科，它这种组织形式跟整本书有什么区别？维基百科其实是把关键信息组成团，然后编成词条。Karpathy 的 Wiki 和维基百科其实在做同一件事：把原始知识编纂成一个一个的 wiki 页面。换句话说，它是从线性的、很长的材料（比如书籍）中，把资料提取出来，编排成一个个词条。这种做法有点像纪传体。就像司马迁写《史记》之前，史书都是编年体的，按时间顺序，一年一年地记，本质上是流水账，是线性的。司马迁做的事情是：他把人物拎出来编条，把这些人物的生平从编年体里抽取出来，编排成一个个列传本纪，像《廉颇蔺相如列传》《项羽本纪》，其实就是一个个 wiki 条目。

所以最早的维基百科编纂者是谁？是司马迁。司马迁做的事情，就是从线性的知识和原始材料里，头翻到尾，把它抽离成纪传体这种类似维基百科的关联结构。实际上《史记》可以算作中国第一部维基百科，司马迁也是中国第一个维基百科编纂者。Karpathy 的 LLM Wiki 其实是让 agent 帮你编纂一部私人百科全书——这种行为就是"司马迁行为"。你原来读一本书的时候是按顺序读的，就像《资治通鉴》一样，是流水账；但你真正关心的是，这件事情发生以后，这个人物后来怎么样了、结局如何，这时候你就必须去看纪传体。

从编年体到纪传体，其意义就在于：当你读到某一条知识以后，是可以追溯到原始记录的，也就是说它保留了一条完整的证据链。你看到那条消息，想去看原文，没问题，这个过程一般由 agent 代劳，你不需要亲自去做。但 Karpathy 的方案有一个问题：你怎么把你构建好的知识库分享出去？这其实是我写 Wiki Graph 的动机之一。

对 Karpathy 来说，schema 决定了你的召回标准：什么东西应该编纂成 wiki，什么东西不编，你自己决定，自己拍板。但我其实希望在实体提取、主谓宾关系这一层，有一个更标准、更有共识的标准。Karpathy 的知识库本质上是对话唠出来的，太私人了。这玩意儿怎么分享给别人？就像我上一个视频说的，你如果真的提取了《西游记》，它最终会跟你的工作日报、每日周报，还有一些乱七八糟的私人信息混在一起，这时候你很难把《西游记》单独抽出来分享给别人，因为这等于要把自己的第二大脑分享出去，这不可能的，你不能像海绵宝宝那样把自己的大脑切一块给别人。

所以我其实想把知识库的粒度和层次压低一点。就像我上一个视频说的，《西游记》最后在 Wiki Graph 里交付出来的是一个封闭的归档。在 Google 的 OKF 里，这个东西占据的是 storage layer 一层。换句话说，我没有破坏 Karpathy 的体系，因为我已经提前把知识里的实体以及主谓宾关系这种结构直接提取出来了，而且我这个标准是对标维基百科的。维基百科里每一个概念或者说每一个实体对应一个 QID，所以我归档出来的这种归档是具有公共知识性的。我把这种带有公共知识性的归档用 U 盘、用网盘也好，或者直接把文件发给别人，别人的第二大脑都可以直接接过来，因为它有共识，不会出现"这个分法跟我们不一样、不兼容"的情况，因为我占据的是 storage layer 那一层，并不影响主谓宾的三元结构。你稍微修饰一下，Karpathy 的那个 schema 其实可以直接拿来用。

我觉得 Karpathy 在分享这个事情上做了取舍，他把这些东西做成了……

Karpathy 那套方案还有一个特点，就是太贵。Karpathy 的方案如果做实体提取必须做取舍。对 agent 来说，你说把整本书都提取出来，agent 肯定会偷工减料，但这种偷工减料是为用户着想，因为如果它真的撸起袖子大干一场，用户的钱包会吃不消。

在 WikiGraph 里我把这个方案从 agent 方案直接退回成 flow 方案。flow 是不是弱了？flow 省钱。而且我提取实体的方案对 AI 来说难度降低了，我不需要大语言模型去猜人类心思，因为标准很明确，直接对齐维基百科就行了。强的大语言模型对人类心思的把握确实非常敏锐，但它也很贵。我给它下简单的任务，反而发现 deepseek 非常合适。deepseek 在这套模式下召回实体非常精准，所以就是靠 deepseek 用 flow 扫书，把每一段话都拆成主谓宾结构，然后做分析。比如"关羽斩了华雄"，主语就是关羽，宾语就是华雄，谓语就是斩，这种三元结构一层嵌套一层，最终把整本书里所有的知识、所有的原文都嵌入一个巨大的网络。这种结构是 AI 最喜欢的，其实就是知识图谱。要提取的东西，如果让 AI 自己扫书，它会偷懒，偷懒本质上是给用户省钱，因为它很勤快地扫完最后买单的是用户。到了我这里，方案直接是开实路让 deepseek 跑，随便烧，反正烧不了多少钱，这样整本书才能真的被扫完；否则 agent 不会真的把整本书扫完。

对上层 agent 来说就很简单了。知识图谱这个巨大的三元结构网络已经建好了，我直接抓 entity。比如我关心关羽，就抓关羽，整本书上所有关于关羽的信息都能被列出来。这时候写关羽的 wiki 词条就好写了。对 Karpathy 那套流程来说，其实对应的就是 entity、concatenate 这些概念，这些东西很快关羽词条就写出来了，agent 不需要再翻全书。翻全书效率很低，RAG 也是做这玩意，也是为了避免在查询阶段去扫全书，但在录入阶段避免不了。Karpathy 预想的场景不是说让你把书塞进知识库里，他说的是今天看到一个网页上的文章很感兴趣，明天看了个视频，后天看了个论文，论文最长也就十几页，让 AI 全部过一遍非常合适。但到书这里的话，可能就得用到 WikiGraph，因为 WikiGraph 专门就是用来扫书的，它扫书用 flow 不会漏掉，所有内容都会给 AI 看。

我还原一下，如果让 agent 去扫《三国演义》，让它把关羽的所有人物关系提取出来。一开始 agent 会一页一页地看，但发现没看到关羽，就全文检索，搜出来关羽的关系过多，然后就开始写代码处理。但文学作品中实体之间的关系本来就是含蓄、模糊的，不适合用代码批量处理，agent 很有可能会干这事儿，因为它不可能不干。

现在想一想，WikiGraph 和 Karpathy 的方案不是对立关系，实际上是互相补充的普通关系。Google 的 OKR 就给了这个项目一个位置，它其实就是偏底层的 storage layer 那一层，Karpathy 的方案是 storage layer 之上，彼此不影响。上层 agent 拿到这种主谓宾结构，而且是事无巨细、覆盖整本书且可信的，每个 entity 又以维基百科词条作为背景板，等于说每个实体在人类公共语义中都有一个精确的、争议不大的位置。对上层 agent 来说，有了这么一个东西，效率会大大提高。

用一句话总结就是：Karpathy 让 agent 编辑你的私人 wiki，但这个私人 wiki 太私人，不好分享；WikiGraph 做了一件更底层的事，就是把一本书或一组文档封装成一个相对封闭的 WikiGraph 知识归档文件，里面有原文、实体、主谓宾关系和证据链。这个归档可以被 agent 查询和使用，也可以被别人接管过去直接使用。它不是 Karpathy 方案的替代品，也不是 Karpathy 方案的实现，其实是在给 Karpathy 那套东西补充一个可分享、可追溯、可以扫描整本书的归档方案和底座。
